# FX ingestion and Bronze-to-Silver processing

Install everything from the repository root with `python -m pip install .`. Use `python -m pip install -e .` for development. All dependencies and command entry points are defined once in pyproject.toml.

## Data and execution

Bronze (`data/0_bronze/`) contains the original trades.xml and securities.csv plus generated currencies.csv. Silver (`data/1_silver/`) contains trades_enriched.parquet. Transformations preserve original Bronze files and column names.

There are two commands in the data pipeline:

1. `trade-api-usd-exchange-rates` reads the currencies and trade dates required by the Bronze inputs, fetches the corresponding USD exchange rates, and generates `data/0_bronze/currencies.csv`.
2. `trade-transform` reads Bronze, enriches the trades and publishes Silver. It requires the `currencies.csv` generated by the first command. If that file is missing, transformation stops with an error and no new Silver dataset is published.

For a complete run with fresh rates, execute both commands from the repository root, in this order:

```powershell
trade-api-usd-exchange-rates
trade-transform
```

If Windows reports `Acceso denegado` when starting either generated `.exe` command (for example, because of a company application policy), invoke the same commands through the virtual environment's Python interpreter:

```powershell
python -m data_pipeline.fx_api
python -m data_pipeline.data_pipeline
```

These module commands run the same code and accept the same options. For example, a historical run is:

```powershell
python -m data_pipeline.fx_api --start-date 2025-01-01 --end-date 2025-01-31
python -m data_pipeline.data_pipeline
```

### How exchange-rate dates are selected

Without date options, `trade-api-usd-exchange-rates` explicitly reads every `tradeDate` in `data/0_bronze/trades.xml`. It parses the timestamps as UTC, finds the earliest and latest UTC calendar dates, and requests rates for that inclusive range. For example, if the trades are dated 15 and 16 January, the command creates validity windows for both dates. It fails without replacing `currencies.csv` if there are no trades or if any `tradeDate` is missing or invalid.

You can override the dates found in `trades.xml` by supplying both `--start-date` and `--end-date`:

```powershell
trade-api-usd-exchange-rates --start-date 2025-01-01 --end-date 2025-01-31
trade-transform
```

Explicit dates are an override: the FX command does not check that they cover the dates in `trades.xml`. You must therefore choose a range that includes every trade you intend to transform. Both options are required together, the range is inclusive, and the end date cannot precede the start date.

If `currencies.csv` already exists and contains rates covering the source trades, you can skip the refresh and run only:

```powershell
trade-transform
```

`trade-transform` always reads these three Bronze inputs: `trades.xml`, `securities.csv`, and `currencies.csv`. A missing file causes the command to fail. If `currencies.csv` exists but has no valid rate window for a trade date, the transformation can still publish the row, but it marks that row as invalid with the `CURRENCY_RATE_NOT_VALID_FOR_TRADE` quality flag and leaves its USD value null.

Frankfurter is the only provider; no API key or `.env` file is needed. Each daily window is [00:00 UTC, 00:00 UTC the next day). Non-publication days use the most recent available daily reference. Every refresh derives its currency list from the current security master, so newly introduced currencies are included automatically.

The FX HTTP API is optional and is not part of the batch pipeline. Start it as a long-running process with:

```powershell
trade-api-usd-exchange-rates --serve
```

The equivalent command that bypasses the generated Windows launcher is `python -m data_pipeline.fx_api --serve`.

API documentation: <http://127.0.0.1:8000/docs>. POST `/currency-rates/refresh` covers source trade dates. POST `/currency-rates/refresh-history?start_date=2025-01-01&end_date=2025-01-31` creates explicit historical daily windows. Both replace the Bronze currency table.

For programmatic use, `refresh_currency_table(now=<timezone-aware datetime>)` creates one rolling validity window covering the 24 hours immediately before `now`. This compatibility path is not used by the installed CLI or HTTP endpoints; those use source trade dates or explicit calendar dates.

## Pipeline stages and naming

`read_bronze` reads XML/CSV and records processing time. `transform_silver` cleans text, applies semantic names/types and calculates local trade value. `enrich_silver` joins securities and exchange rates, calculates USD value and sets quality flags. `semanticize_silver` applies the common published naming rules before `write_silver` publishes files. Reading, transformation, enrichment and writing are separate stages.

`clean_text_values` trims and uppercases textual values before joins, preserving nulls and numeric, timestamp and boolean types. ISO-8601 timestamps with mixed fractional-second and timezone representations are parsed consistently into UTC. Published names and generated quality flags are uppercase. Shared naming rules in silver_semantics.SILVER_DATATYPE_PREFIXES classify actual dtypes:

| Datatype | Prefix | Example |
| --- | --- | --- |
| Integer | INT_ | INT_QUANTITY |
| Floating point | FLOAT_ | FLOAT_FX_RATE_TO_USD |
| Text | STRING_ | STRING_ISIN |
| Boolean | BOOLEAN_ | BOOLEAN_HAS_SECURITY |
| Timestamp | TIMESTAMP_ | TIMESTAMP_TRADE_DATE |
| Duration | DURATION_ | DURATION_ELAPSED |

Quantities use nullable Int64; fractional quantities are rejected without rounding. Naming preserves data, dtypes, row order and row counts. Reapplying semantics does not duplicate prefixes. Ambiguous dtypes, duplicate names, uppercase collisions and incompatible prefixes are rejected.

Joins retain one row per input trade, including duplicate trades and missing reference data. Null or empty ISINs never match securities. `BOOLEAN_HAS_SECURITY` identifies successful security joins independently of currency and FX availability. `BOOLEAN_IS_QUALITY_VALID` is false when a trade has a missing or duplicate trade ID, a side other than BUY/SELL, no security or currency, invalid numeric values or timestamps, a non-positive/non-finite FX rate, or no rate valid for its timestamp. Invalid derived values are published as null rather than infinity. Rate selection uses [valid_from, valid_to) against `tradeDate`. Validity columns are internal and are not published; `FLOAT_FX_RATE_TO_USD` remains in Silver.

Silver is published only as typed Parquet. The generic writer accepts `table_name` for other semanticized Silver tables:

```python
from pathlib import Path
from data_pipeline.data_pipeline import write_silver
from data_pipeline.silver_semantics import semanticize_silver

# customers is a DataFrame with explicit supported types.
write_silver(semanticize_silver(customers), Path("data_pipeline/data/1_silver"), table_name="customers")
```

## Quality checks, logs and publication failures

```powershell
trade quality-checks
trade quality-checks path/to/trades_enriched.parquet
```

Quality checks only read the published file. They report missing securities, null security flags, duplicate or null trade IDs, sides outside BUY/SELL, invalid row-level quality status, and missing or non-finite USD values. Exit code is 0 for a clean report and 1 otherwise.

Processing logs each stage, row counts, security and FX matches, the final schema and output paths. Parquet and currency-table writes serialize to a temporary file beside the destination and atomically replace it only after success. Failures preserve the prior file and report the original cause. The processing CLI exits with code 1 on errors.
